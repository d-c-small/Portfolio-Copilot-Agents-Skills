# CREATE Reporting Layer Stored Procedures Skill

This skill guides you through generating a [create] schema reporting procedure for the Gold (Reporting) layer. CREATE procedures handle one-time table creation and population from EDW Silver layer data using dimensional modeling (Kimball approach).

## When to Use This Skill

Use this skill when:
- The user enters the phrase "Build a [create] schema reporting layer procedure"
- Creating a new reporting table (Dimension or Fact) for the first time
- Building a procedure to perform an initial full data load from EDW to Reporting layer
- You need to follow the naming pattern: `create.[Dim/Fact]_[Entity]`
- Creating stored procedures in the `[create]` schema of the reporting database
- Building dimensional models with star schema patterns

**Do NOT use this skill for:** 
- EDW layer procedures (use the [`create-edw-procedures`](../create-edw-procedures/SKILL.md) skill for those)
- Incremental updates or MERGE operations (use the [`merge-reporting-procedures`](../merge-reporting-procedures/SKILL.md) skill for those)

## Agent Execution Flow

When you receive a request to build a CREATE reporting procedure, follow this sequence:

1. **Consult Resources First** - Read [create-reporting-template.sql](./create-reporting-template.sql) and [examples/create-reporting-example.sql](./examples/create-reporting-example.sql) to understand the expected structure

3. **Determine Table Type** - Is this a Dimension (descriptive attributes) or Fact (measurable events)?

## Key Differences from EDW Layer

| Aspect | EDW Layer | Reporting Layer |
|--------|-----------|-----------------|
| **Methodology** | Bill Inmon (subject-aligned) | Ralph Kimball (dimensional) |
| **Naming** | `[org_subject]` schemas | `[dim]` or `[fact]` schemas |
| **Procedure Pattern** | `create.[org]_[subject]_[SourceSystem]_[Entity]` | `create.[Dim/Fact]_[Entity]` |
| **Data Source** | Raw Bronze tables | EDW Silver tables |
| **Table Types** | Normalized | Dimensional (Dimensions & Facts) |
| **Keys** | Business/Source keys | Surrogate keys, Foreign keys to dimensions |
| **Grain** | Source system aligned | Business process focused |

## Naming Convention

Reporting layer CREATE procedures follow this pattern:

**Pattern for Dimensions:** `create.Dim_[Entity]`

**Pattern for Facts:** `create.Fact_[Entity]`

**Examples:**
- `create.Dim_Project`
- `create.Dim_Date`
- `create.Fact_DailyLogCompletion`
- `create.Fact_Inspections`

**Components:**
- `Dim` or `Fact` - Table type (Dimension or Fact)
- `[Entity]` - Business entity name (Project, Inspection, Date)

## Required Components

Every CREATE reporting procedure must include all of these elements in this exact order:

### 1. Header and SET Options

**Header comment block** (include full attribution):

```sql
-- =============================================================================
-- Procedure: [create].[Dim_Entity]  OR  [create].[Fact_Entity]
-- Description: Initial creation and population of [Entity] dimension/fact table from EDW to Reporting layer
-- Generated by: [AI Agent Name] (e.g., SQL Architect Agent)
-- Created: [Date] (e.g., 01/15/2026)
-- Reviewed By: [User Name or Account]
-- Modified: [Date] [User Name or Account] - [Description of changes]
-- WARNING: Review carefully before deploying to production
-- =============================================================================
```

**SET options (must appear BEFORE CREATE PROCEDURE):**

```sql
SET ANSI_NULLS ON
GO
SET QUOTED_IDENTIFIER ON
GO
```

### 2. CREATE PROCEDURE and Table Structure

Build your procedure starting with CREATE PROCEDURE with these components:

1. **DROP TABLE IF EXISTS** - Clean state before recreating
2. **CREATE TABLE** - Define all columns:
   - Surrogate Key (BIGINT - auto-incrementing or SEQ value)
   - Business/Dimension Keys (references to dimensions)
   - Attribute Columns (dimension attributes or fact measures)
   - LoadHash (VARBINARY(32)) - for change detection
   - LoadDateTime (DATETIME2(7)) - for audit trail
   - UpdateDateTime (DATETIME2(7) NULL) - for future MERGE operations
3. **CTEs (if needed)** - Common Table Expressions for data transformation
4. **INSERT statement** - INSERT INTO followed by SELECT FROM the CTE(s) or source table
5. **Comment** - "Insert transformed data into the target table"

**Key principles:**
- **Match source data types** - Query the EDW source table's column definitions and use the exact same data types in the CREATE TABLE statement
- Include ALL columns in HASHBYTES that future MERGE procedures will monitor
- Hash format: `HASHBYTES('SHA2_256', CONCAT_WS('|', ISNULL(CAST(col AS VARCHAR(8000)), ''), ...))`
- **CTE Placement**: CTEs must come BEFORE the INSERT statement
- Use direct INSERT INTO...SELECT for performance
- For Dimension tables: Include effective/expiration dates if SCD Type 2
- For Fact tables: Include all dimension keys and measures
- Use explicit column lists in INSERT/SELECT (never SELECT *)

## Dimension vs Fact Tables

### Dimension Tables (`Dim.[Entity]`)

Purpose: Store descriptive attributes about business entities

**Typical columns:**
- Surrogate Key (DimensionID or similar)
- Business/Source Keys (e.g., ProjectID)
- Attributes (Name, Status, Description, etc.)
- Effective/Expiration dates (if tracking history)
- LoadHash, LoadDateTime, UpdateDateTime

### Fact Tables (`Fact.[Entity]`)

Purpose: Store measurable events or transactions at a specific grain

**Typical columns:**
- Surrogate Key(s) (FactID or combination key)
- Foreign Keys to Dimensions (links to Dim tables)
- Degenerate Dimensions (hierarchical attributes)
- Measures (numeric facts: counts, amounts, durations)
- LoadHash, LoadDateTime, UpdateDateTime

## Column Requirements

Every procedure must explicitly list these columns:

| Column Name | Type | Purpose | Notes |
|---|---|---|---|
| Primary Key / Surrogate Key | BIGINT or INT | Uniquely identifies rows | Required for MERGE join |
| Foreign Keys (Fact only) | BIGINT | Links to dimension tables | References Dim table keys |
| Attributes/Measures | VARCHAR/INT/DATE/DECIMAL | Entity data or fact measurements | Include all monitored columns in hash |
| LoadHash | VARBINARY(32) | Change detection | `HASHBYTES('SHA2_256', CONCAT_WS('|', ...))` |
| LoadDateTime | DATETIME2(7) | When data was loaded | Set once with GETDATE() |
| UpdateDateTime | DATETIME2(7) NULL | When data was updated | For future MERGE operations |

**Hash calculation principles:**
- Use empty string '' as null placeholder in CONCAT_WS (reporting layer convention)
- Cast all columns to VARCHAR(8000) for consistent hashing
- Include ALL columns that future MERGE will need to monitor for changes
- Calculate hash in SELECT statement with GETDATE() for LoadDateTime

## Validation Checklist

⚠️ **Before considering a CREATE reporting procedure complete, verify ALL items below:**

- [ ] Header comment block complete
- [ ] SET ANSI_NULLS ON and SET QUOTED_IDENTIFIER ON present before CREATE PROCEDURE
- [ ] SET NOCOUNT ON inside procedure body
- [ ] DROP TABLE IF EXISTS statement exists
- [ ] CREATE TABLE with proper schema (dim or fact) and primary key
- [ ] LoadHash column is VARBINARY(32)
- [ ] LoadDateTime column is DATETIME2(7)
- [ ] UpdateDateTime column is DATETIME2(7) NULL
- [ ] All relevant columns included in HASHBYTES calculation
- [ ] Hash uses CONCAT_WS with '' as null placeholder (reporting convention)
- [ ] "Insert transformed data into the target table" comment present
- [ ] INSERT statement lists all columns explicitly
- [ ] SELECT statement matches INSERT column order
- [ ] All database references explicit ([EDW], [dim], [fact], etc)
- [ ] Procedure naming follows pattern: `create.[Dim/Fact]_[Entity]`
- [ ] GO statement at end of procedure

**❌ If ANY item is unchecked, revise the procedure before deployment.**
