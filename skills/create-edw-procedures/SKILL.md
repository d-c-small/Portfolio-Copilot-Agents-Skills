# CREATE Stored Procedures Skill

This skill guides you through generating a CREATE schema stored procedure for the EDW (Enterprise Data Warehouse) Silver layer. CREATE procedures handle one-time table creation and population from raw source data.

## When to Use This Skill

Use this skill when:
- The user enters the phrase "Build a CREATE schema stored procedure"
- Creating a new EDW table for the first time
- Building a procedure to perform an initial full data load from raw to Silver
- You need to follow the naming pattern: `create.[org]_[subject]_[SourceSystem]_[Entity]`
- Creating stored procedures in the `[create]` schema

**Do NOT use this skill for:** Incremental updates or MERGE operations (use the [`merge-edw-procedures`](../merge-edw-procedures/SKILL.md) skill for those)

### ⚠️ Critical Requirement: Always Consult Template and Example

> **When generating a CREATE schema stored procedure, you MUST refer to both the template and working example provided in the "Examples and Templates" section.** Use these as your guide to ensure the generated procedure follows all required components, structure, and best practices outlined in this skill. Do not generate a procedure from scratch without consulting these resources.

## Naming Convention

CREATE procedures in the EDW follow this pattern:

**Pattern:** `create.[org]_[subject]_[SourceSystem]_[Entity]`

**Examples:**
- `create.ac_dailylog_Procore_Completion`
- `create.ae_project_CRM_Account`

**Components:**
- `[org]` - Organization abbreviation (ac, ae)
- `[subject]` - Subject domain (dailylog, project, finance)
- `[SourceSystem]` - Source system name (Procore, Dynamics, OneStream)
- `[Entity]` - Specific entity being loaded (Completion, Account, Budget)

## Required Components

Every CREATE procedure must include all of these elements in this exact order:

### 1. Header and SET Options

**Header comment block** (include full attribution):

```sql
-- =============================================================================
-- Procedure: [create].[org]_[subject]_[SourceSystem]_[Entity]
-- Description: Initial creation and population of [Entity] table from raw to EDW
-- Generated by: [AI Agent Name] (e.g., SQL Architect Agent)
-- Created: [Date] (e.g., 01/15/2026)
-- Reviewed By: [User Name or Account]
-- Modified: [Date] [User Name or Account] - [Description of changes]
-- WARNING: Review carefully before deploying to production
-- =============================================================================
```

**SET options:**

```sql
SET NOCOUNT ON;      -- Reduces network traffic by suppressing row count messages
```

### 2. Table Structure, Transformation, and Insert

Build your procedure with:

1. **DROP TABLE IF EXISTS** - Clean state before recreating
2. **CREATE TABLE** - Define all columns:
   - Primary Key (BIGINT or INT)
   - Data columns (all source columns needed)
   - LoadHash (VARBINARY(32)) - for change detection
   - LoadDateTime (DATETIME2(7)) - for audit trail
   - UpdateDateTime (DATETIME2(7) NULL) - for future MERGE operations
3. **CTE transformation** - Use `_[SourceSystem][Entity]` CTE with HASHBYTES calculation
4. **INSERT statement** - Must use exact comment: "Insert transformed data into the target table"

**Key principles:**
- Include ALL columns in HASHBYTES that future MERGE procedures will monitor
- Hash format: `HASHBYTES('SHA2_256', CONCAT_WS('|', ISNULL(CAST(col AS VARCHAR(8000)), '.'), ...))`
- Use explicit column lists in INSERT/SELECT (never SELECT *)
- CTE must calculate GETDATE() once, not per-row

## Column Requirements

Every procedure must explicitly list these columns:

| Column Name | Type | Purpose | Notes |
|---|---|---|---|
| Primary Key | BIGINT or INT | Uniquely identifies rows | Required for MERGE join |
| Data Columns | VARCHAR/INT/DATE etc | Source entity data | Include all monitored columns in hash |
| LoadHash | VARBINARY(32) | Change detection | `HASHBYTES('SHA2_256', CONCAT_WS('|', ...))` |
| LoadDateTime | DATETIME2(7) | When data was loaded | Set once in CTE with GETDATE() |
| UpdateDateTime | DATETIME2(7) NULL | When data was updated (NULL initially) | For future MERGE operations |

**Hash calculation principles:**
- Use `.` as null placeholder in CONCAT_WS
- Cast all columns to VARCHAR(8000) for consistent hashing
- Include ALL columns that future MERGE will need to monitor for changes
- Calculate in CTE, not per-row in SELECT

## Best Practices

1. **Always drop and recreate** - Use DROP TABLE IF EXISTS to ensure clean state
2. **Transform in CTE** - Keep transformation logic in a single, readable CTE
3. **Name CTEs consistently** - Always use `_[SourceSystem][Entity]` for the main transformation
4. **Include all monitored columns in hash** - Think ahead about what MERGE will need to detect
5. **Use explicit column lists** - Always list columns in INSERT/SELECT, never use SELECT *
6. **Cast consistently** - Apply consistent data types and casts for quality data
7. **Document transformations** - Add comments explaining complex transformations
8. **Use meaningful aliases** - In the source query, use logical column aliases
9. **Preserve source data types** - Only cast when necessary for correctness or hashing
10. **Set LoadDateTime once** - Calculate GETDATE() at CTE level, not per row in SELECT
11. **Cast DATE columns to DATE** - All date/datetime columns in the CTE SELECT statement must be explicitly cast to DATE (e.g., `CAST(VOU_INV_DATE AS DATE) AS InvoiceDate`). This ensures consistent date handling and prevents time component ambiguity in the EDW layer.
